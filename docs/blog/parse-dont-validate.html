Permission checks are parsers

"Parse, don't validate," applied to authorization: make the permission check on a user id return a value only it can create — then require that value where the privilege is used. In Gleam, and in the Clojure it compiles to.

gleam-clj · every snippet below was compiled and run by the compiler in this repo; the error messages are verbatim

Alexis King's Parse, don't validate names a habit good type-driven code shares: when you learn something about a value, record what you learned in its type. A validator inspects data and returns the same data plus a yes/no. A parser inspects data and returns different, more informative data — or an error. The validator's knowledge evaporates one line later; the parser's knowledge is carried by the value itself.

Authorization is the sharpest place to apply this, because the cost of the validator habit is a security bug, not a style complaint.

The validator version, and where it rots

Here is the shape most codebases have. A boolean check, and privileged functions that trust their caller already performed it:

the boolean-blind version
pub fn can_edit(user_id: String) -> Bool

// ...and, somewhere else entirely:
pub fn rename_dashboard(user_id: String, name: String) -> String {
  // hope the caller checked. everyone hopes.
}

Three failure modes, all invisible to the compiler:

  • Boolean blindness. can_edit learned something real and returned True — one bit. Which user? Checked against what? The answer existed for one expression, then vanished.
  • The check and the use drift apart. The call site that checks and the function that acts are held together by convention. Refactors add a new path to rename_dashboard; nothing forces the new path to check.
  • The id is still a string. Empty string, "0", "robert'); DROP" — every function that touches a raw id re-inherits every doubt about it.

Step one: parse the id at the boundary

First, the id itself. An opaque type in Gleam exports the type but not its constructor — so the only way for the rest of the program to obtain a UserId is through the function that scrutinizes the raw string. The doubts are handled once, in one place, and the result is a value that can no longer be empty, negative, or unparsed:

permissions.gleam
pub opaque type UserId {
  UserId(Int)
}

pub type IdError {
  Empty
  NotANumber(String)
  OutOfRange(Int)
}

/// Parse untrusted input into a UserId — the only way to make one.
pub fn parse_user_id(raw: String) -> Result(UserId, IdError) {
  case string.trim(raw) {
    "" -> Error(Empty)
    trimmed ->
      case int.parse(trimmed) {
        Error(_) -> Error(NotANumber(trimmed))
        Ok(n) if n < 1 -> Error(OutOfRange(n))
        Ok(n) -> Ok(UserId(n))
      }
  }
}

Note what the signature says that can_edit(user_id: String) -> Bool could not: the ways this can fail are enumerated in the return type, and the success case hands back a different type than it was given. Downstream code that holds a UserId holds evidence.

Step two: the permission check mints a proof

Now the same move, one level up. Instead of asking "may user 42 edit?" and getting a bit, ask the check to parse the situation — user plus role — into a value that exists only when the answer is yes. The privileged function then demands that value:

permissions.gleam, continued
pub type Role {
  Viewer
  Editor
  Owner
}

pub opaque type CanEdit {
  CanEdit(UserId)
}

pub type Denied {
  Denied(who: UserId, needs: Role)
}

/// Check once, at the boundary. Success mints the proof.
pub fn require_editor(user: UserId, role: Role) -> Result(CanEdit, Denied) {
  case role {
    Editor -> Ok(CanEdit(user))
    Owner  -> Ok(CanEdit(user))
    Viewer -> Error(Denied(user, Editor))
  }
}

/// Demands the proof. Unauthorized calls don't type-check.
pub fn rename_dashboard(proof: CanEdit, name: String) -> String {
  let CanEdit(UserId(id)) = proof
  "user " <> int.to_string(id) <> " renamed dashboard to " <> name
}

Three properties fall out, and none of them depend on discipline:

  • The check can't be skipped. rename_dashboard takes a CanEdit, and only require_editor can construct one. A call site without a check has nothing to pass.
  • The check can't drift from the use. The proof value is the connection; it travels through the code from check to use, visible in every intermediate signature.
  • Denial is data, not absence. Denied(who, needs) carries who was refused and what they lacked — an audit log entry, not a silent False.

The compiler holds the door

Claims about "can't" deserve receipts. Try to use a bare UserId where the proof is required — the diagnostic below is the compiler's actual output, reproduced by this repo's build:

gleam's type checker, verbatim
error: Type mismatch
   ┌─ permissions.gleam:70:20
   │
70 │   rename_dashboard(user, "pwned")
   │                    ^^^^

Expected type:

    CanEdit

Found type:

    UserId

And forging the proof from outside the module fails at the import — opaque exports the type, not the constructor:

from another module, verbatim
error: Unknown module value
  ┌─ app.gleam:1:21
  │
1 │ import permissions.{CanEdit, rename_dashboard}
  │                     ^^^^^^^ Did you mean `type CanEdit`?

`CanEdit` is only a type, it cannot be imported as a value.

The trusted surface of the whole scheme shrank to two short functions — parse_user_id and require_editor. Audit those, and every other call site is covered by the type checker.

What survives the compile to Clojure

This site documents a Gleam → Clojure compiler, so the natural question: what happens to a proof-carrying type when it lands on the JVM, where nothing stops a determined caller from conjuring records? Here is the compiled rename_dashboard, verbatim:

permissions.clj — compiler output, excerpted but unedited
;; type CanEdit
(defprotocol ICanEdit)
(defrecord CanEdit [value] ICanEdit)
(defn CanEdit? "True if `v` is a CanEdit value." [v] (instance? CanEdit v))

(defn rename-dashboard
  "rename_dashboard(proof: CanEdit, name: String) -> String

   Demands the proof. Unauthorized calls don't type-check."
  {:malli/schema [:=> [:cat [:fn CanEdit?] :string] :string]
   :gleam/src "permissions.gleam:52"}
  ^java.lang.String [proof ^java.lang.String name]
  (let [{{id :value} :value} proof]
    (str (str (str "user " (int/to-string id)) " renamed dashboard to ") name)))

The static guarantee is Gleam's; Clojure callers are outside the type checker's reach. But the proof doesn't dissolve into a bare map — it compiles to checkable structure:

  • The docstring carries the contract. (doc rename-dashboard) in any REPL shows the Gleam signature, and :gleam/src points at the line that defines it.
  • The schema demands the proof at runtime. [:fn CanEdit?] is derived from the Gleam type. Turn on malli instrumentation and a Clojure call passing a raw id — (rename-dashboard 42 "x") — throws :malli.core/invalid-input at the boundary instead of misbehaving past it.
  • The same schema feeds clj-kondo, so an obviously wrong call is a static lint error in the editor before anything runs.
Honest asterisk: on the Clojure side (->CanEdit user) is one expression away — records are open construction there. What the compile preserves is the boundary discipline: the proof type, its predicate, and an opt-in runtime check at exactly the functions that demand proof. Inside the Gleam world the guarantee is total; at the interop edge it degrades to an instrumented contract rather than nothing.

What this pattern does and doesn't buy

  • It buys: unskippable checks, error cases you must handle (Result forces the Denied branch), a two-function trusted core, and denial as loggable data.
  • It doesn't buy: resource-level precision — this CanEdit proves edit rights generally, not rights to a particular dashboard. Want that? Same move, one more field: CanEdit(UserId, DashboardId), minted by a check that takes both.
  • It can't buy: freshness. A proof minted at request start can outlive a mid-request revocation, exactly like a session token. Scope proofs to a request; don't cache them.

The pattern generalizes past permissions: non-empty lists, sanitized HTML, verified email addresses, positive amounts. Anywhere the code asks a yes/no question and then acts on the answer somewhere else, there is a type that could carry the yes — parse once, and let the checker chase the value so you don't have to chase the convention.

Run it yourself: the full example lives in the repo as gleam-src/permissions.gleam, gated by CI like every other fixture. clojure -M:repl, then (gl/require-gleam "gleam-src/permissions.gleam"). Its main parses "42", mints the proof, and prints user 42 renamed dashboard to Q3 revenue — on the JVM, byte-identical to what gleam run prints on the BEAM.
